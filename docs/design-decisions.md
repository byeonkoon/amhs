# 설계 결정 기록

물류 관제(ACS·OCS·WMS) 도메인에서 겪은 문제들을 바탕으로, 이 프로젝트에서 어떤 구조를 택했고 왜 그렇게 정했는지 기록한다. 각 항목은 **문제 → 선택 → 이유 → 현재 상태** 순서로 적는다.

이 문서는 설계 판단만 담는다. 특정 제품의 소스·사양·식별자는 포함하지 않는다.

---

## 1. 접수 응답과 실행 완료를 분리한다

**문제.** 장비에 명령을 보냈다는 사실과 장비가 그 동작을 끝냈다는 사실은 다르다. 둘을 한 상태로 합치면 송신 직후 작업이 완료로 넘어가고, 실제로는 움직이지 않은 차량을 두고 다음 작업을 배차하게 된다.

**선택.** 작업 상태와 장비 명령 상태를 별도 머신으로 둔다.

- 작업: `QUEUED → ASSIGNED → TO_SOURCE → LOADING → TO_DESTINATION → UNLOADING → COMPLETED`
- 명령: `CREATED → SENT → ACCEPTED → EXECUTING → SUCCEEDED / FAILED`

타임아웃은 실패가 아니라 **결과 불명**으로 따로 둔다. 응답이 없다는 것은 실패했다는 뜻이 아니라 모른다는 뜻이고, 이 둘을 같게 다루면 이미 수행된 동작을 다시 보내게 된다.

**상태.** 계약 정의 완료, 실행 경로는 미구현.

## 2. 이동 연장 명령은 값 변화로 판정한다

**문제.** 주행 중인 차량에 다음 구간을 이어 붙이는 명령(연속 이동)을 언제 보낼지 정해야 한다. 경과 시간이나 진행률을 기준으로 삼으면 명령을 보낸 시점과 차량 상태가 갱신되는 시점 사이에 간격이 생기고, 그 간격 동안 판단이 흔들린다. 흔들림을 막으려고 유예 시간을 두기 시작하면 그 값이 현장마다 달라져 튜닝 대상이 된다.

**선택.** **목표가 바뀌었을 때만** 연장 명령을 낸다. 같은 목표에는 다시 보내지 않는다.

시간이 아니라 값의 변화를 보므로 판정이 멱등해지고, 유예 타이머가 필요 없다.

**함께 정한 것.** 목표 이력(마지막으로 보낸 목표)은 **접수 응답을 받은 뒤에** 갱신한다. 송신 전에 갱신하면 송신이 실패했을 때 "이미 보낸 목표"로 기록되어 재시도 조건이 성립하지 않고, 그 목표에 대한 연장 명령을 영영 다시 내지 못한다. 단발 통신 실패가 영구 누락으로 굳는 경로를 막는다.

**상태.** 설계 확정, 미구현.

## 3. 장비 상태 신호는 선택적 capability로 다룬다

**문제.** 어떤 장비는 "지금 목적지 변경을 받을 수 있다"는 상태를 보고한다. 그 신호가 있으면 연장 가부를 정확히 알 수 있다. 하지만 모든 장비가 보고하지는 않으며, 제조사·프로토콜마다 다르다.

**선택.** 신호가 **없는 것을 기본**으로 두고, 있으면 정밀도를 높이는 보강으로 쓴다.

- 장비 capability에 신호 제공 여부를 두고 기본값은 false.
- false면 2번의 값 변화 판정만으로 동작한다.
- true면 그 조건에 장비 신호를 AND로 더한다. 불필요한 발행이 줄지만, 없다고 동작이 깨지지 않는다.

특정 장비에만 있는 신호를 전제로 설계하면 그 장비 밖에서는 성립하지 않는다.

**상태.** 설계 확정, 미구현.

## 4. 동선은 그래프 구조로 분리한다

**문제.** 천장 레일로 다니는 차량과 바닥으로 다니는 차량이 한 평면도에 그려지면, 화면에서 겹쳐 보이는 지점이 실제 충돌 지점인지 구분되지 않는다. 겹쳐 보인다는 이유로 충돌 자원을 묶으면 서로 막을 이유가 없는 두 차량이 대기한다.

**선택.** 레이어 컬럼 같은 별도 축을 만들지 않고 **실제 노드·구간 연결로 분리**한다. 서로 이어지지 않은 그래프면 경로 탐색이 자연히 갈린다.

차종별 접근 제한은 포트에 둔다. 포트에 접근 가능 차종을 두고 출발·도착 양쪽을 검사해 배차 후보를 정한다. 같은 설비라도 차종별 접근점이 다르면 별도 포트로 등록한다.

두 동선이 실제로 만나는 곳은 인수인계 지점뿐이므로, 거기서만 동시 접근을 직렬화한다.

**상태.** 데이터 모델과 seed 반영 완료. 배차 연동은 미구현.

## 5. 제어 권한을 장비별로 구분한다

**문제.** 자체 시뮬레이터나 직접 제어하는 차량은 서버가 경로와 예약을 소유한다. 반면 제조사 RCS가 경로를 소유하는 차량은 목적지만 주고 세부 경로는 장비가 정한다. 같은 차량의 세부 경로를 두 관제기가 동시에 소유하면 충돌한다.

**선택.** 장비별로 `CONTROLLER_MANAGED` / `VENDOR_MANAGED`를 구분하고, 후자는 목적지 명령과 공유 구역 조정으로만 연동한다.

**상태.** 구분 정의 완료, 어댑터 미구현.

## 6. 통신 파라미터는 장비별로 관리한다

**문제.** 전역 설정 하나로 통신 방식을 고르면 서로 다른 프로토콜의 차량을 한 사이트에서 함께 운영할 수 없다. 연장 명령 사용 여부 같은 동작 옵션도 마찬가지다.

**선택.** 차량마다 통신 종류, 프로토콜 종류와 버전, 제조사, 연결·프로토콜 profile을 둔다. 동작 옵션도 전역 플래그가 아니라 차량 profile 속성으로 둔다.

**상태.** 스키마와 설정 API 구현, SQL 통합 테스트 통과.

**변경 (2026-09-30).** 통신 방식(PC/PLC/MQTT)은 사이트 운영 옵션에서 한 번 고르도록 바꿨다. 한 사이트에 서로 다른 통신 방식의 차량을 섞지 않는다는 운영 기준을 따른 것이다. 대신 같은 MQTT 사이트 안에서 제조사·버전이 다른 차량은 함께 운영할 수 있도록, VDA 패킷·동작 값을 이름 있는 VDA 프로파일로 묶고 차량은 프로파일 하나만 지정한다.

- 프로파일 항목: 인터페이스, 토픽 버전, 제조사, JSON 버전, 출발지 동작, 목적지 동작. 토픽 버전과 JSON 버전은 서로 따르지 않으므로 따로 둔다.
- 여러 값을 한 문자열에 나열하는 방식은 쓰지 않는다. 동작 이름에 구분자가 들어가거나 항목 순서가 바뀌어도 오류 없이 저장되기 때문이다.
- 통신 방식이 MQTT가 아니면 차량의 프로파일은 비워 둔다. MQTT 사이트에서 사용하는 차량은 프로파일이 필요하다. MQTT에서 다른 방식으로 바꾸려면 차량의 프로파일을 먼저 비워야 한다.
- 운영 옵션에는 한 번의 진입 허가에 담을 최대 노드 수도 둔다.
- 기존 차량별 통신 바인딩(접속 대상·외부 식별자)과 새 구조의 정리는 후속이다.

## 7. 송신 원장과 업무 트랜잭션을 함께 기록한다

**문제.** 작업 상태를 바꾸는 것과 장비에 명령을 보내는 것이 따로 커밋되면, 한쪽만 반영된 상태로 서버가 멈출 수 있다.

**선택.** 작업 상태 변경·이력·송신할 명령을 하나의 DB 트랜잭션에 기록하고, 실제 송신은 그 원장을 읽어 수행한다. 재송신해도 같은 명령 식별자를 쓴다. 수신 이벤트는 식별자와 순번으로 중복·역순을 걸러낸다.

명령이 중복 전송될 수 있다는 전제를 유지한다. end-to-end exactly-once를 주장하지 않고, 장비 쪽 중복 처리로 효과를 보장한다.

**상태.** 최소 구조 정의, 미구현.

## 8. 재시작과 점유 해제를 보수적으로 다룬다

**문제.** 서버가 재시작되면 미완료 작업과 장비 실제 상태가 어긋날 수 있다. 통신이 끊겼다는 이유로 점유 구간을 해제하면, 실제로는 그 구간에 있는 차량과 충돌한다.

**선택.**

- 재시작 시 `RECOVERING` 모드로 진입하고, 미완료 작업과 장비 상태를 대조한 뒤에 배차를 연다.
- 통신 단절이나 예약 유효기간 경과만으로 점유를 해제하지 않는다. 위치가 불명한 구간은 격리하고 운영자 확인을 요구한다.
- 교착은 대기 관계 감지·알람·수동 복구를 먼저 구현한다. 자동 해결은 후속 범위로 둔다.

**상태.** 규칙 정의, 미구현.

## 9. 진단 화면은 실제로 읽어올 수 있는 값만 둔다

**문제.** 정합성이나 장애 복구를 화면에 나열해도 값을 얻을 경로가 없으면 빈 화면이 된다.

**선택.** 표준 라이브러리로 수집 가능한 항목만 둔다. 네트워크 인터페이스 링크 상태와 오류 수, 무선 AP 신호세기와 접속 대수, 관제 PC의 CPU·메모리·디스크, JVM heap. 수집은 애플리케이션 메트릭, 호스트 정보 라이브러리, 네트워크 장비 조회로 한다.

작업 정합성은 기준일과 비교일을 골라 그날의 작업 원장을 집계한다. 정상처리 비율 = 완료 ÷ (완료 + 중간취소 + 실패)이며, 진행 중 작업은 결과가 확정되지 않아 분모에서 뺀다. 분모 정의를 화면에 적어 둔다. 합의되지 않으면 같은 날의 정합성이 사람마다 달라진다.

**상태.** 화면 설계 완료, 미구현.

## 10. 완료 보고는 소비될 때까지 보존한다

**문제.** 장비가 보낸 완료 신호를 수신부가 받아 상태에 기록하는데, 그 상태를 읽어 다음 단계로 넘기는 주체는 제어 루프다. 수신이 계속 들어오는 동안 기록이 덮이면, 제어 루프가 읽기 전에 완료 신호가 사라질 수 있다. 그러면 작업은 완료됐는데 서버는 모르는 상태가 된다.

**선택.** 종료 상태(성공·실패)는 **해당 작업 단계가 읽어갈 때까지 덮어쓰지 않는다.** 읽어간 뒤에 해제한다.

생산자와 소비자가 다른 주기로 도는 구조에서는 이런 보존 규칙이 없으면 신호가 유실된다.

**상태.** 설계 확정, 미구현.

## 11. 완료 보고 매칭은 다중 키로 한다

**문제.** 명령 식별자 하나로만 완료 보고를 맞추면, 늦게 도착한 이전 작업의 보고를 현재 작업의 것으로 오인할 수 있다. 재시도나 통신 지연이 있으면 실제로 일어난다.

**선택.** 액션 종류, 진행 단계, 작업 식별자가 **모두 일치할 때만** 그 보고를 현재 작업의 결과로 인정한다. 하나라도 어긋나면 무시하고 기록만 남긴다.

**함께 정한 것.** 화물 유무 같은 물리 상태는 **완료 보고를 받은 뒤에만** 바꾼다. 명령을 보낸 시점에 바꾸면 실패했을 때 재고와 실제가 어긋난다.

**상태.** 설계 확정, 미구현.

## 12. 알 수 없는 위치로 상태를 덮지 않는다

**문제.** 장비가 보고한 위치가 등록되지 않은 노드일 수 있다. 그 값을 그대로 현재 위치에 넣으면 이후 경로 계산과 예약이 모두 잘못된 전제 위에서 동작한다.

**선택.** 등록되지 않은 위치 식별자는 **무시하고 이전 위치를 유지**하며 로그를 남긴다. 위치가 불명확한 상태를 그럴듯한 값으로 메우지 않는다.

같은 원칙이 구간 점유에도 적용된다. 통신이 끊겼다는 이유로 점유를 해제하지 않고 격리한다(8번 참조).

**상태.** 설계 확정, 미구현.

## 13. 경로 완료와 액션 완료를 구분한다

**문제.** 이동이 끝난 것과 그 지점에서 수행할 동작(적재·하역)이 끝난 것은 다른 사건이다. 둘을 한 신호로 다루면 단일 구간 반송에서는 문제가 없지만, 여러 구간을 이어 가는 반송에서는 어디까지 끝났는지 판단할 수 없다.

**선택.** 이동 상태와 액션 상태를 **별도 신호로 받고 별도로 판정**한다. 작업 완료는 두 조건이 모두 충족될 때 성립한다.

**상태.** 설계 확정, 미구현.

## 14. 기능 없는 제조사 식별 칸은 스키마에서 제거한다

**문제.** 포트에 장비 제조사를 구분하는 문자열 칸이 있었다. 어떤 로직도 이 값으로 분기하지 않고 저장과 화면 표시만 했다. 값이 비어 있어도 실제 제조사·고객사 실명이 들어갈 자리만 제공한다.

**선택.** 해당 칸을 **DB·서버 계약·화면·문서에서 제거**한다. 이미 적용된 마이그레이션은 체크섬 때문에 수정하지 않고 뒤에 오는 마이그레이션에서 열을 삭제한다. 반대로 VDA5050 `manufacturer`는 공개 표준이 토픽 경로에 요구하는 기능 필드이므로 유지하고, 저장소에는 placeholder 값만 둔다.

**이유.** 기능이 없는 칸은 지워도 동작이 바뀌지 않는다. 남겨 두면 검토할 때마다 값이 채워졌는지 확인해야 하고, 한 번 채워지면 이력에 남는다. 유지 비용이 없는 쪽을 택했다.

**상태.** 구현·검증 완료(전체 83개 테스트 통과, 스킵 없음).

## 15. 예약 단위는 노드로 두고 구간은 양끝으로 판정한다

**문제.** 두 차량이 같은 구간을 마주 보고 진입하면 충돌한다. 구간을 따로 예약하면 노드와 구간 두 종류의 점유를 항상 일치시켜야 하고, 둘이 어긋나는 순간이 곧 사고다.

**선택.** **노드만 예약**한다. 구간은 양끝 노드를 같은 차량이 쥐고 있을 때만 통과할 수 있다.

**이유.** 마주 보는 두 차량은 같은 노드를 먼저 요구하게 되므로 정면 충돌이 노드 경합으로 자동 해결된다. 관리할 점유 종류가 하나면 어긋날 자리도 없다.

**상태.** 구현·검증 완료.

## 16. 이동 허가는 현재 위치부터 연속된 구간만 준다

**문제.** 계획 경로 중 일부가 막혔을 때, 막힌 곳을 건너뛰고 그 뒤를 함께 허가하면 차량은 앞이 뚫린 것으로 읽는다.

**선택.** 현재 서 있는 노드부터 **연속된 접두부**만 부여하고, 처음 막힌 노드에서 멈춘 뒤 그 뒤로는 재개하지 않는다. 길이는 사이트 운영 옵션의 허가 노드 수를 넘지 않는다. 짧게 받는 것은 실패가 아니라 그만큼만 가고 다시 요청하는 정상 동작이다.

**이유.** 허가는 계획이 아니라 지금 점유해도 되는 범위다. 도달할 수 없는 지점을 포함한 허가는 장비 쪽에서 구분할 방법이 없다.

**상태.** 구현·검증 완료.

## 17. 점유 해제는 도착 근거로만 한다

**문제.** 시간이 지났다는 이유나 명령을 보냈다는 이유로 점유를 풀면, 아직 그 자리에 있는 차량의 노드를 다른 차량에게 넘길 수 있다.

**선택.** 차량이 **더 앞선 노드에 있다고 보고했을 때만** 그 뒤의 점유를 푼다. 타이머·명령 송신·통신 두절 어느 것도 해제 사유가 아니다. 허가하지 않은 노드를 보고하면 아무것도 풀지 않고 불일치로 드러낸다. 작업이 끝나도 차량이 서 있는 노드는 계속 잡아 두고 앞쪽만 돌려준다. 위치를 아는 주체가 없으면 하나도 풀지 않는다.

**이유.** 정보가 없는 것은 없다는 근거가 아니다. 장비 명령의 결과 불명 처리와 같은 원칙이다([설계 결정 14 이전 항목](design-decisions.md) 및 진행 기록의 장비 명령 아웃박스 참조).

**상태.** 구현·검증 완료.

## 18. 교착은 탐지해서 알리고 자동으로 풀지 않는다

**문제.** 서로가 가진 노드를 요구하는 차량들은 스스로 빠져나올 수 없다. 그러나 이를 자동으로 해소하려면 한 대를 물러나게 해야 한다.

**선택.** 대기 관계를 기록하고 **닫힌 사슬을 찾아 보고**한다. 각 차량은 한 번에 한 곳만 기다리므로 사슬을 따라가면 끝나거나 처음으로 돌아오고, 돌아오는 경우가 교착이다. 보고 시점에 그 노드를 아직 그 차량이 쥐고 있는지 다시 확인해 이미 풀린 사슬은 알리지 않는다. 해소는 하지 않는다.

**이유.** 후진은 물리 동작이고 별도의 이동 명령과 안전 판단이 필요하다. 제어기가 조용히 결정할 일이 아니다.

**상태.** 탐지·보고 구현·검증 완료. 해소 절차는 미구현.

## 19. 연장 판단은 시간 간격이 아니라 미해결 명령으로 한다

**문제.** 이동 중 허가를 연장하는 명령을 연달아 보내면 겹치는 허가가 장비에 도달한다. 기존 현장 시스템은 고정 시간 간격으로 이를 막았다.

**선택.** **아직 수신 확인되지 않은 연장 명령이 있으면 다음 것을 만들지 않는다.** 시간은 조건이 아니다.

**이유.** 막아야 하는 것은 "겹치는 연장"이고, 시간 간격은 그것을 근사했을 뿐이다. 간격이 짧으면 겹치고 길면 차량이 불필요하게 선다. 미해결 여부를 직접 보면 근사가 필요 없다. 결과가 영영 불명인 명령은 운전자가 처리하며, 그때까지 그 작업의 연장은 멈춘다.

**상태.** 구현·검증 완료.

## 20. 연장은 계획 경로를 따르고 다시 계획하지 않는다

**문제.** 연장할 때마다 현재 위치에서 다시 경로를 계산하면, 새 경로가 이미 확보한 노드와 갈라질 수 있다. 쓰지도 않을 노드를 쥔 채 다른 노드를 요구하게 된다.

**선택.** 배차 시점에 산정한 경로를 배정에 저장하고 연장은 그 경로를 따라간다.

**이유.** 예약과 계획이 갈라지지 않아야 한다. 경로 자체를 바꿔야 하는 상황은 연장이 아니라 재계획이며 별도로 다룬다.

**상태.** 구현·검증 완료. 재계획은 미구현.

## 21. DISTANCE 판정의 기준은 한 번의 완전한 허가 거리로 둔다

**문제.** "출발 시 허가된 거리의 몇 %가 남았는가"를 그대로 구현하려면 출발 시 허가 길이를 보관해야 한다. 그런데 노드는 통과할 때마다 반납되므로 판정 시점에는 그 길이가 이미 사라지고 없다.

**선택.** 남은 허가 거리를 **경로 앞쪽으로 한 번의 완전한 허가에 해당하는 거리**와 비교한다. 거리는 노드 좌표 사이로 계산하며, 이 모델에 구간 실제 길이가 없기 때문이다.

**이유.** 답하려는 질문("한 번의 허가에 비해 남은 것이 얼마나 적은가")은 같고, 기준값이 시점에 따라 사라지지 않는다. 구간 실제 길이가 생기면 좌표 계산을 대체한다.

**상태.** 구현·검증 완료. 구간 실제 길이는 미확인.

## 22. 연장은 남은 경로로 판단하고, 끝이 가까우면 세운다

**문제.** 남은 허가가 짧아질 때마다 연장하면 목적지 직전까지 연장이 이어지고, 정지해야 할 지점에서도 차량이 달리는 명령을 받는다.

**선택.** 제어기가 남은 허가 노드 수로 연장 시점을 정하되, 차량 앞에 남은 허가가 **연장 하한보다 적어 이미 정지를 준비하는 중이거나 허가 끝이 정지 노드이면 연장하지 않는다.** 남은 허가가 하한 이상이고 연장 기준 이하일 때만 연장한다. 정지 노드는 허가를 그 노드에서 끝낸다. 허가를 다 쓰고 선 차량에는 새 이동 명령을 보낸다. 차량이 목적지 변경 가능 신호를 줄 때만 연장하는 방식은 운영 옵션이며 기본은 끈다.

**이유.** 연장은 달리는 차량의 목적지를 바꾸는 명령이다. 허가 끝에 거의 다 와 이미 감속하는 차량에는 바꾸기보다 세우고 다시 출발시키는 편이 차량이 받는 명령의 의미가 분명하다. 차량 신호를 기본 조건으로 두면 신호를 주지 않는 차량은 연장을 영영 받지 못하므로 선택으로 둔다.

**상태.** 구현·검증 완료. 정지 노드 지정·하한 값의 현장 기준은 미확인.

## 23. 합류 순서는 먼저 기다린 차량이 정한다

**문제.** 노드 점유만 보면 합류 노드가 비는 순간 먼저 요청을 다시 보낸 차량이 들어간다. 오래 기다린 차량이 계속 밀릴 수 있다.

**선택.** 합류 지점으로 지정한 노드는 대기 기록의 시작 시각이 이른 차량에게 먼저 허가한다. 대기 시각은 같은 노드를 계속 기다리는 동안 유지한다. 보고가 끊긴 차량의 대기는 순서에 넣지 않는다. 판단 주체를 운영 옵션으로 두어, 차량 쪽 신호로 합류를 판단하는 방식으로 바꾸면 제어기는 점유만 본다.

**이유.** 순서를 정하는 근거가 기록에 남아 있어야 나중에 왜 그 차량이 먼저 갔는지 설명할 수 있다. 끊긴 차량의 대기가 순서를 쥐면 살아 있는 차량이 영영 못 간다.

**상태.** 구현·검증 완료. 차량 신호 방식의 실제 신호는 미구현.

## 24. Zone 정원이 차면 갈림길에서 서지 않고 돈다

**문제.** 정원이 찬 Bay 앞에서 차량을 세우면 그 자리가 본선이라 Bay에서 나오는 차량과 뒤따르는 차량을 함께 막는다.

**선택.** Zone은 노드 묶음과 정원을 가진다. 밖에서 Zone 노드로 처음 들어가는 허가는 안의 차량 수가 정원보다 적을 때만 준다. 안의 차량은 Zone 노드를 허가로 쥐었거나 그 노드에 서 있다고 보고한 차량이다. 진입을 거절당한 차량은 Zone을 지나지 않는 순환 경로를 갈림 노드 뒤에 끼워 본선을 한 바퀴 돌고 다시 시도한다. Zone 안에서의 이동과 퇴출은 막지 않는다.

**이유.** 정원 판정과 차량 흐름을 같이 지켜야 한다. 서서 기다리는 것보다 도는 편이 본선을 비워 두고, 안의 차량이 빠져나갈 길도 막지 않는다.

**상태.** 구현·검증 완료. 작업 없이 Zone에 남은 차량의 퇴출은 결정 30.

## 25. 취소는 송신과 같은 잠금 아래에서 판단한다

**문제.** 취소가 작업을 끝내고 점유를 푸는 사이, 송신기는 그 작업의 이동 명령을 가져갈 수 있었다. 차량은 이미 비워진 길을 따라 움직이게 된다.

**선택.** 취소는 작업 행을 잠근 뒤 그 작업의 명령 행을 송신기와 같은 행 잠금으로 기다려 잡는다. 나가지 않은 명령은 **철회** 상태로 바꾸고 작업을 끝낸다. 송신 중·송신됨·수신 확인 명령이 하나라도 있으면 출발 전 취소여도 **취소 요청**으로 두고 할당과 점유를 유지한다. 정지가 확인되면 끝내며, 적재가 시작된 적이 없는 작업이면 화물 복구로 보내지 않는다.

**이유.** 차량이 받았을 수 있는 명령이 있으면 차량이 멈췄다는 증거가 올 때까지 그 길은 차량의 것이다. 철회는 삭제가 아니라 기록으로 남겨, 결정했다가 거둬들인 사실을 감출 수 없게 한다.

**상태.** 구현·검증 완료. 송신 중 취소의 실제 동시 실행은 미검증.

## 26. 복구 종료는 화물 위치의 진술이다

**문제.** 복구 대기 작업에 같은 취소 확인을 한 번 더 보내면 화물 위치를 모르는 채로 작업이 끝났다.

**선택.** 복구 대기에서의 일반 전이는 화물 위치가 기록되기 전에는 거부하고, 같은 취소 확인은 아무것도 바꾸지 않는다. 복구 종료는 별도 요청으로, 화물이 출발지 또는 목적지에 있다는 진술과 확인 방법을 받아 위치를 기록한 뒤 각각 취소 또는 완료로 끝낸다. 차량 위나 모름은 답이 아니다.

**이유.** 보호 상태를 만든 이유가 화물 위치를 모른다는 것이므로, 그것을 아는 사람의 진술 없이는 풀리면 안 된다.

**상태.** 구현·검증 완료. 장비 완료 증거로 위치를 기록하는 경로는 미구현.

## 27. 이동 허가는 작업 단계가 정한다

**문제.** 접근·반송 경로를 합쳐 허가하면 빈 차량이 출발지를 지나 목적지로 갈 수 있는 명령이 나갔다. 복구·취소 대기 작업에도 연장이 나갔다.

**선택.** 경로는 합쳐 저장하고 출발지 위치를 함께 저장한다. 적재 전에는 출발지까지만, 반송 단계에서는 끝까지 허가한다. 배정·출발지 이동·반송 단계만 이동 단계로 보고, 그 밖의 단계에서는 연장·재출발을 만들지 않으며 그 단계로 넘어갈 때 나가지 않은 이동 명령을 철회한다. Zone 순환 경로가 출발지 앞에 끼면 출발지 위치를 그만큼 민다.

**이유.** 허가는 차량이 지금 해도 되는 일의 범위다. 작업 단계가 바뀌면 그 범위도 바뀐다.

**상태.** 구현·검증 완료.

## 28. 한 차량의 명령은 하나씩, 기록된 순서대로 나간다

**문제.** 행 잠금 건너뛰기는 같은 명령의 중복 송신만 막고, 연장이 자기가 늘리는 이동 명령을 앞지르는 것은 막지 못했다.

**선택.** 명령에 차량을 기록하고, 같은 차량의 앞선 명령이 대기·송신 중(결과 불명 포함)·재시도 대기이면 다음 명령을 가져가지 않는다. 가져온 묶음은 기록 순서로 정렬한다.

**이유.** 장비는 받은 순서대로 해석한다. 결과를 모르는 명령 뒤에 다음 명령을 붙이면 무엇을 기준으로 해석할지 정할 수 없다.

**두 층의 기준(재검토 후 명시).** 이 순서 규칙은 **회선 순서**에 대한 것이다. 앞선 명령이 회선에 나갔으면(송신됨) 뒤 명령도 나갈 수 있다. 앞선 것이 이미 같은 순서로 장비에 닿았기 때문이다. 반면 연장·재출발·Zone 퇴출을 **새로 만들지** 말지는 장비의 수신 확인으로 판단하며, 송신됨은 아직 미해결로 본다. 둘을 같은 기준으로 묶으면 수신 확인을 돌려주지 않는 프로토콜의 차량은 첫 명령 뒤에 큐가 영영 멈춘다. 프로토콜별로 무엇을 수신 확인으로 볼지는 통신 계약(A02/A25)에서 정한다.

**상태.** 구현·검증 완료. 여러 송신기의 실제 동시 실행은 미검증.

## 29. 실제 위치는 허가보다 우선한다

**문제.** 허가 없이 어떤 노드에 서 있다고 보고한 차량은 점유 원장에 없어서, 다른 차량이 그 노드를 허가받을 수 있었다.

**선택.** 허가를 줄 때 다른 차량이 마지막으로 서 있다고 보고한 노드는 그 허가의 주인이 누구든 내주지 않는다. 보고가 끊긴 위치도 센다. 교착 탐지에서도 그 차량을 막는 쪽으로 센다. 원장은 보고만으로 고치지 않는다.

**이유.** 원장은 허락한 것을, 보고는 실제를 말한다. 둘이 다르면 실제를 따르고, 원장을 임의로 덮어쓰지 않는다.

**상태.** 구현·검증 완료. 불일치 보고를 이력으로 남기는 것은 미구현.

## 30. 작업을 마치고 Zone에 남은 차량은 작업 없는 이동으로 내보낸다

**문제.** Zone 안의 포트에서 작업을 마친 차량이 서 있으면 정원을 계속 차지해, 진입을 거절당한 차량은 끝없이 본선을 돈다. 이 차량에게는 이동을 실어 보낼 반송 작업이 없다.

**선택.** 장비 명령을 작업이 아니라 사이트와 차량에 속하게 하고, 작업이 없는 명령을 허용한다. 실행 스윕은 배차를 먼저 한 뒤, 작업 없이 Zone 안에 정지한 차량마다 **퇴출 이동**을 연다. 목적지는 Zone 밖에서 합류 지점·포트·다른 차량이 서 있거나 허가를 쥔 노드를 뺀 곳 중 경로 비용이 가장 작은 노드다. 퇴출 이동은 차량당 하나만 열리고 경로를 저장한다. 받은 허가를 다 쓰고 선 뒤에만 이어 주며, 같은 차량의 앞선 명령이 정리되지 않았으면 보내지 않는다. 퇴출 중인 차량은 배차하지 않고, 목적지에 서면 닫는다.

**이유.** 정원 제한과 순환 대기는 안에 있는 차량이 언젠가 나간다는 전제가 있어야 끝난다. 작업 없는 이동을 작업처럼 꾸미면 화물·상태 머신의 의미가 흐려지므로 별도 기록으로 둔다. 합류 지점과 포트를 피하는 것은 그 자리가 다른 차량이 반드시 지나가거나 작업이 올 곳이기 때문이다.

**상태.** 구현·검증 완료. 차량의 홈 노드가 Zone 밖이고 비어 있으며 도달 가능하면 그곳을 먼저 쓴다(누군가 그 차량을 위해 고른 자리이므로). 퇴출 현황 화면, 실장비 주행은 미구현·미검증.

## 31. 송신 결과는 명령을 되돌리지 못한다

**문제.** 수신 확인과 송신 결과는 따로 도착한다. 확인이 먼저 오면 뒤늦은 송신 결과가 예외로 끝나 같은 묶음의 나머지 명령을 송신 중 상태로 남겼다. 또 취소 때 이미 송신 중이던 이동 명령은 철회할 수 없어, 그 송신이 실패로 끝나면 재시도 대기로 돌아가 다시 나갈 수 있었다.

**선택.** 수신 확인된 명령에 늦게 온 송신 결과는 기록만 하고 상태는 그대로 둔다. 취소·비이동 단계 전환 때 송신 중인 명령에는 **철회 요청**을 남기고, 그 송신이 장비에 닿지 않았다고 확인되면 재시도 대신 철회로 끝낸다. 닿았다면 송신됨으로 남겨 취소 확인 절차가 다룬다. 송신기는 한 명령의 결과 기록이 실패해도 나머지 묶음을 계속 처리한다.

**이유.** 장비가 받았다는 사실은 나중 소식으로 약해지지 않는다. 취소된 작업의 명령이 실패 덕분에 다시 살아나면 취소가 송신기 경합에 진다.

**상태.** 구현·검증 완료. 실제 송신기 동시 실행은 미검증.

## 32. 차량 하나는 한 번에 한 실행 주체만 가진다

**문제.** 배차와 Zone 퇴출이 서로의 미확정 기록을 보지 못한 채 같은 차량을 동시에 잡을 수 있었다. 또 사용 중지된 차량도 퇴출 이동을 받았다.

**선택.** 퇴출도 배차와 같은 차량 잠금을 잡고, 잠금 아래에서 배정·퇴출 기록과 차량 상태를 다시 읽어 결정한다. 배차도 잠금 뒤 퇴출 중인지 다시 확인한다. 여러 차량은 id 오름차순으로 잠근다. 사용 중지되었거나 자동 작업에서 제외된 차량은 퇴출로도 옮기지 않으며, 열려 있던 퇴출은 닫는다.

**이유.** 먼저 확정한 쪽을 나중 쪽이 반드시 보게 하는 공통 잠금이 있어야 두 원장이 따로 있어도 한 차량을 함께 소유하지 않는다. 사람이 쓰지 말라고 한 차량은 제어기가 스스로 움직이지 않는다.

**상태.** 구현·검증 완료(두 실제 트랜잭션 양방향 시험). 자동 작업 제외가 퇴출까지 막는 것은 신규 설계 선택이며 현장 정책 확인이 필요하다.

## 33. 화물 위치는 증거로만 바뀐다

**문제.** 적재·하역 완료가 자유 문자열 사유만으로 처리되고 화물 위치는 갱신되지 않아, 취소·복구 판단이 늘 "위치 모름"에서 출발했다. 이적재가 실제로 일어나지 않은 경우 다시 시도할 길도 없었다.

**선택.** 전이는 증거(종류·관련 명령·화물 위치)를 받는다. 적재 완료(적재→반송)는 화물이 차량에, 하역 완료(하역→완료)는 목적지에 있다는 증거가 있어야 하며, 화물 위치를 같은 트랜잭션에서 바꾸고 이력에 증거와 함께 남긴다. 시스템 기록 종류는 화물 위치를 정하지 못한다. 센서가 이적재가 일어나지 않았음을 보이면(적재 중 화물이 출발지, 하역 중 화물이 차량) 이동 단계로 돌아가 재시도하고, 작업별 시도 횟수가 운영 옵션 상한에 이르면 복구 대기로 보낸다. 현장 확인·운전자 결정 종류는 식별된 사람만 기록할 수 있으며, 접근 게이트를 통과한 실제 주체를 이력에 남긴다.

**이유.** 화물 위치는 취소·복구·완료 판단의 근거라서 추측으로 채우면 그 판단이 모두 추측이 된다. 기존 현장 시스템은 센서가 이적재 미수행을 보이면 이동 단계로 돌아가 다시 시도했고(상한 없음), 동작 결과 기반 프로토콜은 그 자리에서 멈췄다. 신규는 두 경우를 모두 담되 무한 반복은 막는다.

**상태.** 구현·검증 완료. 장비 센서·동작 보고를 증거로 바꾸는 어댑터, 기본 재시도 상한 값의 현장 확인은 후속.

## 34. 시뮬레이터는 통신 규격이 아니라 시스템 자신의 계약을 말한다

**문제.** 통신 계약(A25)이 정해지기 전에는 실제 장비 없이 반송 전체 흐름을 돌려 볼 방법이 없었다. 규격을 추측해 흉내 낸 시뮬레이터는 규격이 확정되면 버려야 하고, 틀린 추측을 맞는 것처럼 보이게 만들 수 있다.

**선택.** 서버 안의 시뮬레이션 채널이 명령 아웃박스에서 나간 이동·연장 명령의 허가 노드 목록을 그대로 받아 한 단계에 한 노드씩 이동하고, 위치·정지 상태를 보고하며, 수신 확인은 다음 단계에 보낸다. 출발지·목적지에서는 적재 센서 전이를 증거로 보고한다. 설정(`amhs.simulation.enabled`)으로만 켜지고, 켜져 있으면 배치되지 않은 차량의 명령은 "전달 안 됨"으로 남는다. 자동 실행(`amhs.simulation.auto-run`)은 별도 설정이다. 시뮬레이션 상태는 메모리에만 있어 재시작하면 차량을 다시 배치해야 한다.

**이유.** 시스템의 공통 명령과 증거 계약만 쓰면 규격과 무관하게 배차·교통·연장·이적재·증거 판정이 실제로 맞물리는지 확인할 수 있다. 실제 규격으로 접속하는 외부 시뮬레이터는 어댑터 검증(A13/A23) 몫으로 남긴다.

**상태.** 구현·검증 완료. 화면 조작·여러 대 혼합 시험·시간 기반 이동은 후속.

## 35. 차량 상태는 모드와 상태 두 축으로 받는다

**문제.** 원격 여부와 정지 여부 두 플래그만으로는 반자동, 에러, 일시정지, 충전, 적재·하역 중, 리셋을 구분할 수 없었다. 운전자는 차량이 왜 명령을 받지 않는지 알 수 없었다.

**선택.** 기존 현장 시스템처럼 모드(수동·반자동·원격)와 상태(대기·이동·에러·일시정지·충전·적재·하역·리셋)를 따로 받아 저장한다. 제어기가 판단에 쓰는 원격·정지 플래그는 두 값에서 나온다(원격 모드만 원격, 대기 상태만 정지). 두 값을 보내지 않는 보고는 플래그에서 두 값을 만들어 이전과 같이 읽힌다. 화면은 두 축과 화물 유무를 따로 보여 준다.

**상태.** 구현·검증 완료.

## 36. 수동 이동은 작업 없는 이동으로 하고 기존 조건을 지킨다

**문제.** 운전자가 차량을 원하는 노드로 보낼 방법이 없었다.

**선택.** 차량과 목표 노드를 받아 작업 없는 이동(Zone 퇴출과 같은 경로 저장·이어 주기)을 연다. 조건은 기존 현장 시스템의 수동 이동과 같다: 사용 중, 원격 모드, 대기 상태, 진행 중인 작업과 경로 없음, 목표 노드가 지도에 있고 사용 가능. 여기에 상태 신선도, 미정리 명령 없음, 다른 이동 없음을 더한다. 자동 작업 제외 차량도 운전자가 직접 움직일 수 있다(사용 중지 차량은 안 됨).

**상태.** 구현·검증 완료. 이동 중단·취소 조작은 미구현.

## 37. 작업 목록은 진행 중인 것만, 끝난 것은 이력에서

**선택.** 작업 화면과 운전 현황은 끝나지 않은 작업만 보여 준다. 완료·취소·실패한 작업은 이력 화면에서 상태 전이와 사유·조작 주체를 함께 본다.

**상태.** 구현·검증 완료.

## 38. 시뮬레이션은 사이트의 운전 모드다

**문제.** 시뮬레이터가 서버 시작 설정으로만 켜져, 운전자가 화면에서 시뮬레이션과 실제 장비 운전을 고를 수 없었다. 시뮬레이션 차량도 하나씩 직접 배치해야 했고, 화면은 실제 모드와 관계없이 늘 "시뮬레이션"이라고 표시했다.

**선택.** 운영 옵션에 운전 모드(SIMULATION·OPERATION)를 둔다. 명령 채널은 명령이 속한 사이트의 모드를 보고 시뮬레이션 차량 또는 장비 어댑터로 보낸다. 주기 실행은 SIMULATION 사이트에만 돈다: 사용 중인 차량을 자동 배치하고 실행 스윕과 차량 한 단계를 진행한다. OPERATION으로 바뀐 사이트는 시뮬레이션에서 빠진다. 수동 배치·단계 실행 API는 SIMULATION 사이트에서만 받는다. 모드 변경은 다른 옵션처럼 관리자 권한과 유지보수 상태를 요구한다.

**이유.** 실제 장비가 있는 사이트에 가상 위치가 섞이면 안 되므로, 모드가 명령 경로와 보고 출처를 함께 결정해야 한다. 같은 판단 로직(배차·교통·증거)이 두 모드에서 그대로 돌기 때문에 시뮬레이션 결과가 운영 로직의 검증이 된다.

**상태.** 구현·검증 완료. 운전 중(RUNNING) 모드 전환 정책은 유지보수 상태 요구로만 막혀 있다.

## 39. 연장·사용 중지·시뮬레이터는 차량이 보고한 상태를 따른다 (416a5c3 리뷰 F1–F4)

**문제.** 리뷰에서 네 가지가 나왔다. (F1) MORE 연장이 "대기가 아님"을 "이동 중"으로 읽어, 에러·일시정지·충전·적재·하역·리셋을 보고한 차량에도 연장을 냈다. (F2) 수동 이동 중인 차량을 사용 중지하면 이동 기록만 닫히고, 아직 나가지 않은 MOVE 명령은 계속 송신 대상으로 남았다. (F3) 시뮬레이터가 수동·일시정지 보고를 무시하고 차량을 움직이며 상태를 원격·대기로 덮어썼다. (F4) 이력 화면이 조회 실패를 "끝난 작업이 없습니다"로 보여 줬다.

**선택.**
- 연장은 상태가 MOVING인 차량에만 낸다. 대기는 기존대로 `VEHICLE_NOT_MOVING`, 그 밖의 상태는 `VEHICLE_STATUS_<상태>`로 거부한다. 상태 없이 보고한 구형 보고는 대기 플래그에서 상태를 얻는다. 예약·위치는 건드리지 않는다.
- 사용 중지(또는 자동 작업 제외)된 차량의 열린 이동은, 작업에 속하지 않은 그 차량의 명령 중 나가지 않은 것(PENDING·FAILED)을 철회하고, 송신 중인 것은 철회 요청을 표시한다. 송신 중·송신 후 응답 대기 명령이 있거나 차량이 알려진 노드에서 대기로 서 있지 않으면 `<사유>_STOPPING`으로 이동과 경로를 유지한다. 둘 다 아니면 이동을 닫고 차량이 선 노드 앞쪽 예약을 푼다. 새 명령은 보내지 않는다.
- 시뮬레이터는 모드가 REMOTE가 아니거나 상태가 ERROR·PAUSED·CHARGING·RESET이면 그 자리에서 같은 모드·상태를 다시 보고하고 움직이지 않는다(`HELD_<모드|상태>`). 원격·대기로 다시 보고되면 이어서 진행한다. Fleet 화면의 차량 상세에 시뮬레이션 운전 중에만 상태 주입 버튼(원격·대기, 수동, 일시정지, 에러, 충전)을 두었다. 이 입력은 차량 상태 보고 API를 그대로 쓰고 출처는 SIMULATED로 기록된다.
- 이력 화면은 조회 실패를 실패로 표시하고 다시 읽기 버튼을 둔다. 이전에 읽은 목록은 지우지 않는다.

**이유.** 연장은 달리는 차량의 허가를 끊기지 않게 하는 수단이라, 서 있거나 고장 난 차량에 허가를 늘리면 다른 차량의 길만 막는다. 사용 중지는 "더 보내지 않는다"는 뜻이지만 이미 나간 명령은 되돌릴 수 없으므로, 차량이 섰다는 증거가 있을 때까지 길을 쥐고 있어야 실제 위치와 예약이 어긋나지 않는다. 시뮬레이터가 운전자 입력을 덮어쓰면 수동·고장 상황의 판단 로직을 시험할 수 없다.

**상태.** 구현·회귀 시험 완료. 송신 후 장비 응답이 끝내 오지 않는 명령의 정리(시간 초과·복구 절차)는 A25 통신 계약에서 정한다. 그 전까지 이런 이동은 `_STOPPING`으로 남는다.

## 40. 멈춘 이동은 차량의 응답으로 끝나고, 시뮬레이터는 구간을 속도대로 주행한다 (bfd76a2 재리뷰 G1·G2)

**문제.** (G1) 사용 중지된 차량의 이동이 ACK 뒤에 새 보고가 없어도, 명령 전의 IDLE 보고나 한 시간 전 오프라인 보고만으로 끝나며 앞쪽 예약을 풀었다. 명령을 받은 차량은 풀린 노드로 들어갈 수 있었다. (G2) 시뮬레이션 상태 버튼이 화면이 마지막으로 읽은 위치를 다시 보내, 그 사이 한 노드 나아간 차량을 과거 위치로 되돌렸다. 또 차량이 노드에서 노드로 뛰어 움직였고, 구간은 직선만 그릴 수 있었으며, 포트는 설비가 아니라 코드로만 표시됐다.

**선택.**
- 멈출 이동에 정지 결정 시각을 남긴다(V28 `stop_requested_at`). 이 이동의 명령이 하나도 차량에 닿지 않았으면 바로 끝낸다. 닿았을 수 있으면(송신 중·송신·수신 확인) 차량이 정지 결정 **이후** 보낸 신선한 보고에서 온라인·알려진 노드·IDLE일 때만 끝내고 앞쪽 예약을 푼다. ACK는 수신 증거이지 정지 증거가 아니다. 보고 시각과 정지 시각은 트랜잭션 시작 시각이 아니라 실제 시각(`clock_timestamp()`)으로 기록해 같은 트랜잭션 안에서도 순서를 가린다.
- 시뮬레이션 상태 변경은 전용 동작 `PUT …/simulation/vehicles/{id}/state`(mode·status만)으로 한다. 위치·화물은 서버의 시뮬레이터 상태에서 그대로 가져오며, 요청에 위치가 있어도 쓰지 않는다. 주행 틱과 같은 잠금 아래에서 처리한다.
- 차량 파라미터에 주행 속도(mm/s, 기본 OHT 2000·AGV 1000, 신규 설계 값)를 둔다. 실행 루프는 0.2초마다 경과 시간 × 속도만큼 구간을 따라 차량을 움직이고, 노드 사이에서는 좌표만 보고한다(`x_mm`/`y_mm`). 노드는 다음 노드에 도착할 때 바뀌고 그때 뒤쪽 예약이 풀린다. 교통 판단은 계속 노드 기준이다(사용자 확정 규칙과 같다). 시험과 수동 tick은 기존처럼 한 번에 한 노드다.
- 구간에 곡률(`curve_mm`)을 둔다. 구간 가운데가 직선에서 벗어나는 거리이며, +는 시작→끝 방향의 왼쪽(평면도 기준)이다. 2D·3D 그림과 시뮬레이터 주행이 같은 2차 곡선을 쓴다. 경로 비용은 바꾸지 않는다.
- 포트에 설비(equipment unit)를 연결할 수 있고, 지도는 포트 코드 대신 설비 이름을 표시한다. 시험용 가상 설비 7개를 시드로 넣었다(실제 현장 이름 아님).
- 2D에서는 OHT와 AGV를 같은 사각형으로 그리고 색으로만 구분한다. 차량 ID는 굵은 흰 글씨로 쓴다. 차량별 대기 노드(home)와 충전 노드를 지도에 표시하고, 설정 화면에서 대기 노드와 속도를 고른다.

**이유.** 이미 명령을 받은 차량을 멈췄다고 보려면 그 결정 뒤의 차량 말이 필요하다. 위치를 보고하는 것은 차량(여기서는 시뮬레이터)뿐이어야 화면 지연이 위치를 되돌리지 않는다. 노드 기준 교통을 유지한 채 좌표만 더하면 안전 판단을 바꾸지 않고 움직임을 보여 줄 수 있다.

**상태.** 구현·회귀 시험 완료. 곡선 구간의 MORE DISTANCE 판정은 여전히 노드 사이 직선 거리를 쓴다. 장비가 좌표를 보고하는 경로(A25)와 충전 진입·복귀 정책(A34)은 미구현이다. 레거시 곡선·속도 정의는 미확인이다.

## 41. 수동 이동 중지와 내부 STOP 명령

**문제.** 운전자가 보낸 수동 이동을 중간에 멈출 방법이 없었다. 허가는 한 번에 여러 노드가 나가므로, 더 허가하지 않는 것만으로는 차량이 목표까지 가 버린다.

**선택.**
- `POST …/vehicles/{id}/move/stop`은 운전자의 수동 이동(MANUAL)만 멈춘다. Zone 퇴출 이동은 다음 스윕에서 다시 시작되므로 여기서 멈추지 않고, 자동 작업 제외로 멈춘다. 열린 이동은 `GET …/vehicle-moves`로 조회한다.
- 중지는 사용 중지와 같은 정지 절차(결정 40)를 쓴다. 정지 결정 시각을 남기고, 나가지 않은 명령은 거둬들이며, 더 허가하지 않는다. 차량에 명령이 닿았을 수 있으면 내부 명령 `STOP`을 한 번 큐에 넣는다. STOP은 철회 대상에서 빠지고, 이동이 닫힐 때 아직 나가지 않았으면 철회한다. 그래야 늦게 도착한 STOP이 다음 이동을 끊지 않는다.
- 시뮬레이터는 STOP을 받으면 지금 달리는 구간의 끝 노드에서 서고, 서 있었다면 그 자리에 머문 뒤 대기로 보고한다. 이동은 그 보고(정지 결정 이후·온라인·IDLE)로 닫히고 앞쪽 예약이 풀린다.

**이유.** 이미 나간 허가는 되돌릴 수 없으므로 차량 쪽 정지가 있어야 중지가 의미를 가진다. STOP을 MOVE·MORE와 같은 시스템 내부 용어로 두면, 판단 로직과 시뮬레이션은 지금 검증하고 회선 표현은 통신 계약에서 정할 수 있다.

**상태.** 구현·회귀 시험 완료(신규 설계, 기존 시스템의 이동 취소 근거는 찾지 못함). STOP의 회선 표현·장비 응답·급정지 여부는 A25 계약에서 정한다. OPERATION 모드에서는 어댑터가 없어 STOP도 나가지 않으므로, 이동은 차량이 허가 끝에서 설 때 닫힌다.

## 42. 노드 사이의 차량은 대기가 아니다, 화면은 보고 궤적을 재생한다 (5b9909d·ee93086 재리뷰 H1·H2)

**문제.** (H1) 구간 중간에서 화면의 "원격·대기"를 넣으면 nodeId는 지나온 노드인 채 IDLE이 저장되고, 정지 판정이 이를 정지로 보고 이동을 닫으며 앞쪽 예약을 풀었다. 차량은 남은 허가로 다음 노드까지 갔다. (H2) 구간 중간에서 재개하면 좌표는 나아가는데 상태는 IDLE로 남았다. 화면에서도 차량이 0.5초 간격으로 끊어 움직였다.

**선택.**
- 노드 사이 좌표가 있는 차량은 무엇을 보고했든 대기(idle)가 아니다. 이 규칙은 차량 상태 조회 한 곳에서 적용하므로 배차·재출발·Zone 퇴출·수동 이동 판단이 모두 따른다. 정지 완료는 노드 위(좌표 없음)·IDLE·정지 결정 이후·신선한 보고일 때만 인정한다. STOP은 그때까지 유지한다.
- 시뮬레이터는 노드 사이를 달리는 동안 좌표와 MOVING을 한 번에 보고한다(구간 중간에서 재개할 때도). 노드 사이에서 원격·대기로 돌려받으면 차량은 계속 달리므로 MOVING으로 저장한다.
- 표현: 서버 주행 틱을 0.1초로 줄이고, 화면은 위치를 0.3초마다 받는다. 각 보고의 시각(서버 기준)으로 궤적을 쌓아 약 0.6초 뒤를 매 프레임 보간해 그린다. 받는 간격이나 지연이 아니라 차량 자신의 속도가 보인다. 2D와 3D가 같은 버퍼를 쓴다. 3D는 진행 방향으로 차체를 돌린다.

**이유.** 교통은 노드 단위로 판단하므로, 노드에 서 있다는 사실만 정지와 대기의 증거가 될 수 있다. 화면 지연 0.6초는 운전 판단이 아니라 표시 문제이고, 판단은 서버가 최신 보고로 한다.

**상태.** 구현·회귀 시험 완료. 화면 표시 위치는 실제 보고보다 약 0.6초 늦다(표시 전용).

## 43. 상태·좌표 갱신은 한 문장, 화면 보간은 서버 시각만, 차량 표시는 기존 색 체계 (0944784 재리뷰 I1·I2)

**문제.** (I1) 시뮬레이션 상태 변경과 멈춤 재보고가 "위치 지우기 → 좌표 복원" 두 번의 저장이라, 그 사이 정지 판단이 노드 위 IDLE로 오인해 이동을 닫을 수 있었다. (I2) 보고 이력이 없는 차량의 브라우저 시각이 서버 시계 보정에 섞여 이동 차량의 보간이 멈출 수 있었다. 화면에서는 2D 이동 중 상태색이 잘 보이지 않았고, 차량이 세그먼트 위가 아니라 노드 위쪽에 떠 있었으며, 3D 차량이 배경과 비슷했다.

**선택.**
- 모드·상태 변경은 차량 행 하나를 갱신하는 SQL 한 문장이다(노드·좌표·화물 유지). 노드 사이에서 원격·대기는 MOVING으로 저장한다. 이 갱신은 정지 판단이 잡는 같은 행 잠금을 따른다. 시뮬레이터의 멈춤 재보고도 같은 문장을 쓴다.
- 화면 보간의 시계 보정은 실제 보고 시각만 쓴다. 보고가 없는 차량은 설정 위치로 따로 그린다.
- 2D 차량: 세그먼트 위 보고 좌표에 몸체를 놓고 진행 방향으로 회전한다. 채움색은 기존 시스템의 상태색 체계를 따른다(대기·이동(MORE 포함)·알람·일시정지·충전·적재/하역·수동·연결 끊김). 테두리는 호출 가능 상태다(초록: 작업 할당 가능, 회색: 불가 — 사용 중이고 배차 허용인지). 몸체 가운데 원은 화물 유무다(초록/비활성색). 리셋은 일시정지색, 반자동은 수동색(신규 설계).
- 3D 차량: OHT·AGV 모두 흰색 몸체에 호출 가능 색 윤곽선. 상태색은 띠·램프·바닥 원. 배경·바닥은 중간 톤, 포트는 푸른 회색, 화물은 초록 상자.

**이유.** 정지 판단이 보는 행은 한 순간도 "위치 없음"을 거치면 안 된다. 보고 시각이 없는 값은 시계 정보가 아니다. 표시 색은 현장 운전자가 이미 익숙한 체계를 유지한다.

**상태.** 구현·회귀 시험 완료. 상태색 체계는 기존 확인됨(근거는 저장소 밖 기록), 화물 원의 초록·호출 가능 테두리·3D 흰색 차체는 사용자 지시에 따른 신규 표시.

## 44. 혼합 차종 운용: 배차 순서, 화물 적재 차량 제외, 포트·화물 단일 선점 (A23, A10 잔여)

**문제.** OHT 2대·AGV 2대를 함께 돌리자 세 가지가 드러났다. 자동 배차가 대기 작업을 최신 접수 순으로 처리해, 나중 작업이 앞선 작업의 포트를 먼저 차지했다. 화물을 실은 차량이 배차 후보에서 빠지지 않았다. 포트와 화물 ID의 중복 선점을 막는 장치가 없었다.

**선택.**
- 자동 배차는 우선순위 높은 순 → 접수 시각 → ID 순으로 처리한다(A10 설계대로).
- 화물을 실은 차량은 배차 후보에서 빠지고, 잠금 후 재검증에서도 같은 기준을 쓴다(기존 시스템의 후보 제외 조건과 같음).
- 포트 단일 선점(신규 설계): 차량을 잡고 있는 작업은 출발 포트를 적재가 끝날 때까지, 도착 포트를 작업이 끝날 때까지 점유한다. 두 포트 중 하나라도 다른 작업이 쓰고 있으면 `PORT_IN_USE`로 대기한다. 배차는 두 포트에 대한 잠금을 포트 ID 순으로 먼저 잡은 뒤 확인하므로, 두 배차가 같은 포트를 동시에 비었다고 볼 수 없다.
- 화물 ID 단일 선점(신규 설계): 같은 화물 ID로 끝나지 않은 작업이 있으면 접수를 `CARRIER_IN_TRANSPORT`로 거부한다. 같은 화물 ID에 대한 잠금 아래에서 확인한다.
- 샘플 사이트에 OHT-02·AGV-02(가상)를 추가했다.

**이유.** 한 포트에서는 한 번에 한 번의 이적재만 일어날 수 있고, 한 화물은 한 곳에만 있다. 오래된 작업이 먼저 처리돼야 새 작업이 자원을 가로채지 않는다.

**상태.** 구현·혼합 시험 완료. 남은 한계: 작업 없이 경로나 포트 노드에 서 있는 차량은 다른 차량을 위해 비켜 주지 않는다(회피 이동 미구현). 포트 점유 기준과 화물 ID 중복 거부가 현장 규칙과 맞는지는 확인이 필요하다.

## 45. 작업 없는 차량의 회피와 홈 복귀

**문제.** 작업을 마친 차량이 경로나 포트 노드에 그대로 서 있으면, 그 노드를 지나야 하는 차량이 끝없이 기다린다(A23 혼합 시험에서 확인). 작업 없는 차량을 홈으로 돌려보내는 동작도 없었다.

**선택.**
- 회피(신규 설계, 기존 시스템의 회피 의도를 반영): 다른 차량이 `yieldAfterSeconds`(기본 5초) 넘게 기다리는 노드에 작업 없는 차량이 서 있으면 그 차량을 옮긴다. 옮길 곳은 기다리는 차량이 쥔 노드·원하는 노드·남은 경로를 피한, 차량의 홈(비어 있고 갈 수 있을 때) 또는 가장 가까운 빈 자리다. 빈 자리 기준은 Zone 퇴출과 같다(합류 지점·포트·남이 선 곳 제외). 대상은 사용 중·자동 작업 허용·원격·노드 위 대기·신선한 보고·작업/이동/미정리 명령 없음인 차량뿐이다. 그 밖의 차량은 `YIELD_<이유>`로 남긴다.
- 홈 복귀(기존 확인됨): 홈 노드가 설정된 차량이 작업이나 이동을 마친 뒤 `homeReturnSeconds`(기본 0 = 끔) 넘게 할 일이 없으면 홈으로 보낸다. 화물이 있거나, 다른 차량이 홈에 서 있거나 쥐고 있거나 그리로 가는 중이면 보내지 않는다.
- 둘 다 기존 작업 없는 이동(relocation, 목적 YIELD·HOME)으로 처리하므로 예약·연장·정지·사용 중지 규칙이 그대로 적용된다.

**이유.** 노드 단위 교통에서 서 있는 차량은 길을 막는 자원이다. 운전자 개입 없이 정체가 풀려야 한다.

**상태.** 구현·시험 완료. 기존 시스템의 회피 노드 목록(지정 노드로만 회피)과 비용 기준 홈 탐색은 미구현이다. 홈·회피 이동 중인 차량은 도착할 때까지 배차하지 않는다(기존 시스템은 작업이 우선).

## 46. 배차 대기열 전체 순회, 적재 뒤 출발 포트 해제 유지 (6814694 리뷰 J1·J2)

**문제.** (J1) 자동 배차가 대기열 앞 200건만 보았다. 앞쪽 작업이 모두 배차될 수 없으면 뒤의 다른 차종 작업이 평가되지 않았다. (J2) 적재를 마친 작업이 취소·복구 상태로 가면, 상태 이름만 보고 이미 해제된 출발 포트를 다시 점유한 것으로 계산했다.

**선택.**
- 자동 배차는 우선순위 → 접수 시각 → ID 순으로 대기열 끝까지 200건 단위 키셋 페이지로 순회한다. 차종마다 그 순간 배차 가능한 차량 수를 먼저 센다. 0이 된 차종은 첫 작업만 실제로 시도해 정확한 대기 사유를 얻고, 같은 차종의 나머지 작업은 같은 사유로 기록하고 넘어간다.
- 출발 포트는 적재 전 단계(배정·출발지 이동·적재)에서 점유한다. 취소 요청·복구 대기에서는 화물 위치가 차량이나 목적지로 확인되지 않았을 때만 점유한다. 목적지 점유 규칙은 그대로다.

**상태.** 구현·회귀 시험 완료.
