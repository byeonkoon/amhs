# 상위 시스템 통보 계약

반송 지시를 보낸 쪽에 **그 작업이 어떻게 끝났는지** 알려 주는 계약입니다.

지시는 전부터 REST로 받고 있었습니다(`POST /transport-orders`, `Idempotency-Key` 포함). 그런데 나가는
길이 없어서, 지시를 보낸 시스템은 **계속 물어봐야** 했습니다. 1분이면 끝나는 작업이라면 낭비일 뿐이지만,
사람 손을 기다리며 멈춘 작업이라면 **위에서는 아무도 모릅니다** — 그 작업은 느린 것처럼 보일 뿐
막혔다는 사실이 전해지지 않습니다.

## 언제 보내는가

작업이 **스스로 더 진행하지 않는 지점**입니다.

| 상태 | 뜻 |
|---|---|
| `COMPLETED` | 끝났습니다 |
| `CANCELLED` | 취소됐습니다 |
| `FAILED` | 실패했습니다 |
| `RECOVERY_REQUIRED` | **사람을 기다립니다.** 화물이 어딘가에 있고 누군가 확인해야 합니다 |

`RECOVERY_REQUIRED`는 종단 상태가 아닙니다. 사람이 정리하면 그 뒤에 `COMPLETED`·`CANCELLED`·`FAILED`로
가고, 그때 **한 번 더** 보냅니다. 상태가 바뀌었으니 그것이 맞습니다.

통보는 **상태를 바꾸는 트랜잭션 안에서** 기록합니다. 롤백된 전이가 일어나지도 않은 일을 알리거나, 커밋된
전이가 통보를 잃는 일이 없습니다.

## 보내는 모양

```http
POST {설정한 URL}
Content-Type: application/json
Idempotency-Key: order-1234-COMPLETED
{설정한 인증 헤더}: {값}
```

```json
{
  "event": "transport-order",
  "orderId": 1234,
  "siteId": 1,
  "status": "COMPLETED",
  "reason": null,
  "idempotencyKey": "WMS-2026-10-14-0001",
  "sourcePortCode": "BAY-O01",
  "destinationPortCode": "STK-O03",
  "carrierCode": "CAR-00917",
  "endedAt": "2026-10-14T19:03:11.244+09:00",
  "requestSource": "wms"
}
```

- `idempotencyKey` — **지시를 보낼 때 그쪽이 적었던 키**입니다. 상위 시스템이 자기 작업을 알아보는
  열쇠이므로 반드시 넣습니다. `orderId`는 이 데이터베이스의 것이고 바깥에서는 뜻이 없습니다.
- 포트는 **코드**로 말합니다. 지시가 들어온 말과 같은 말입니다.
- `Idempotency-Key` 헤더는 `order-{id}-{status}` 형태로 한 통보마다 하나입니다. **재전송은 같은 키를
  그대로 다시 보냅니다** — 이 관제가 지시를 받을 때 요구하는 것과 같은 예의입니다.

## 전송 결과 판정

장비 명령과 **같은 세 가지 문제**이고 같은 모양으로 답합니다.

| 응답 | 판정 | 왜 |
|---|---|---|
| `2xx` | **SENT** | 받았습니다. 더 할 일이 없습니다 |
| `4xx` | **REFUSED** | 거절도 **답**입니다. 다시 보내도 같은 답이므로 재시도하지 않고 그대로 남깁니다 |
| `408` · `429` | 재시도 | 거절이 아니라 "나중에"라는 말입니다 |
| `5xx` · 타임아웃 · 연결 실패 | 재시도 | **아무도 모릅니다.** 받았는데 답이 유실됐을 수 있습니다 |
| 재시도 상한 도달 | **ABANDONED** | "실패"가 아닙니다. **도달 여부를 알 수 없다**는 뜻이고, 그것이 사실입니다 |
| 설정으로 요청을 만들 수 없음 | **REFUSED** | 보낼 수 없는 헤더나 못 읽는 주소입니다. 재시도해도 같으므로 설정을 고쳐야 합니다 |

`REFUSED`와 `ABANDONED`를 나눈 이유가 전부입니다. "그쪽이 아니라고 했다"와 "알 수 없다"는 다른 사실이고,
합치면 둘 중 하나를 잃습니다.

재시도 간격은 2초부터 **두 배씩**, 최대 5분입니다. 호스트가 밤새 죽어 있어도 재접속으로 저녁을 보내지
않습니다.

**한 작업의 통보는 쓰인 순서로 나갑니다.** 회수 대기가 실패해 기다리는 동안 완료가 먼저 나가 버리면,
위에서는 끝난 작업이 다시 회수 대기로 보입니다. 앞선 통보가 아직 빚으로 남아 있으면 뒤엣것은 기다립니다 —
앞엣것을 포기하거나(`ABANDONED`) 거절당하면 더는 빚이 아니므로 그때 나갑니다. 본문의 `sequence`는 같은
문을 한 번 더 잠그는 것으로, 받는 쪽이 자기 사정으로 순서가 섞여도 어느 것이 나중인지 알 수 있게 합니다.

## 설정

`PUT /api/v1/sites/{site}/configuration/host` — Lv4 관리자, 유지보수 상태.

| 칸 | 뜻 |
|---|---|
| `url` | 보낼 주소. `http://` 또는 `https://`만 받습니다 |
| `authHeader` · `authValue` | 인증에 쓸 헤더 이름과 값 |
| `timeoutMs` | 200~30000. 기본 3000 |
| `maxAttempts` | 1~50. 기본 8 |
| `enabled` | 꺼 두면 아무것도 나가지 않고 **쌓입니다**(잃지 않습니다) |

**`authValue`는 비밀입니다.** 들어가기만 하고 나오지 않습니다. 세 가지로 갈립니다.

| 보낸 값 | 결과 |
|---|---|
| `null`(생략) | 저장된 값을 **그대로 둡니다**. URL만 고치려다 자격증명이 지워지지 않습니다 |
| `""`(빈 문자열) | **지웁니다.** 이것이 없으면 한 번 넣은 자격증명을 뺄 방법이 없습니다 |
| 그 외 | 바꿉니다 |

계정 비밀번호와 같은 규칙입니다. 화면에서는 빈 입력이 `null`로 가므로, 인증을 끄려면 **헤더 이름**을 비웁니다.

리다이렉트는 따라가지 않습니다. 인증 헤더를 다른 호스트로 흘리게 되기 때문입니다.

## 무엇이 나갔는지 보기

자원 구성의 **상위 통보** 탭에 설정과 최근 통보가 함께 있습니다. "이 설정으로 보내고 있다"와 "그 결과는
이렇다"는 호스트가 화요일부터 전부 거절하고 있을 때 같은 질문이고, 두 화면으로 나누면 누군가 답을 들고
오가야 합니다.

`GET /api/v1/sites/{site}/configuration/host/notices` — 같은 내용의 API입니다(`state`·`attempts`·`lastError`).

## 아직 아닌 것

- 작업 **진행 중** 통보(배차됨, 픽업함). 지금은 멈추는 지점만 알립니다. 진행 상황이 필요한 상위 시스템은
  여전히 조회해야 합니다.
- 상위 시스템별 어댑터. 지금은 이 계약 하나이고, 그쪽 모양에 맞추는 변환은 앞단에 두는 것을 전제합니다.
  차량 쪽에서 매핑 문서가 한 일을 여기서는 아직 하지 않습니다.
- 실제 상위 시스템과의 연동 검증. 시험 JVM 안의 HTTP 서버를 상대로만 확인했습니다.
